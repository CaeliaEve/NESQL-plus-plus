# Native infusion rules

Implementation notes for the current unverified batch. This is not a release or game acceptance receipt.

`NativeInfusionRecipes` reads registered `InfusionRecipe` definitions before any NEI display factory. `InfusionLegacyInputs` captures their actual greedy input comparison. The NEI TC4Tweaks conversion API is a different rule: its ingredient factory and enhanced matcher cannot be substituted for the base recipe's own `matches`. Exact enhanced recipes use `InfusionInputSource` for their source-bound predicate graph and the inherited constructor array for the independent cycle phase; see `native-infusion-inputs.md` for the ordered independent-stock projection, including differing cardinalities.

The new `nativeInfusion` process carries the original central definition, comparison mode, ordered requirements, original template ore memberships, relevant native ore-member matches, and observed input comparison state. Predicate templates have only registry/metadata/NBT and do not request item display names, tooltips or icons. In particular a wildcard 32767 is not sent through `Facts.item`; only observed concrete choices enter the content-rendering chain. Native `NBTBase.toString` is captured as data instead of reconstructed from canonical JSON. Registered templates stay borrowed and read-only in the admitted comparison; the native startup method copies the offered center once and pedestal inputs twice. During later consumption the altar compares the pedestal directly against a component copied once at startup, without startup's wildcard metadata rewrite. Both comparison phases have separate observations and preserve their own first-match order. A candidate must satisfy both before being advertised as a usable one-item specimen. An identity that collapses distinct native comparison states is rejected explicitly.

Display choices are exact one-item specimens. They are not an exhaustive list of valid NBT or evidence of an obtainable state. The process defines the wider condition. Query/client/detail hydration includes its observed concrete item facts and aspect facts; raw templates remain predicates. The webpage gates combined choices using native greedy matching and labels its material totals as conditional.

The revolver's nested aspect loop only updates existing map values. Every pass doubles each signed int; after 32 passes all results are zero. The exporter computes this same final value without repeating a potentially enormous loop. It preserves all aspect entries and signed results. This does not change general aspect quantities: signed costs are permitted only in the explicit native-infusion contract.

Ethereal familiar data binds the real BY_NAME map, target and transitive augment/condition graph, accepted item classes and default Java locale. Each specimen records native original/copied augment-key order and lowercase observations. Unknown names preserve their ordered null-dereference behavior. Output replaces malformed `augments` with a compound, whereas the golem's malformed `upgrades` and revolver's malformed list retain detached-write behavior. An owned valid specimen may complete the target's actual preconditions; it does not pretend that the registered center's example aspect/metadata restricts the native matcher. The output projection accounts for `Products.observe` already making the single native copy, avoiding an extra order-changing copy.

The altar calls `getContainerItem(stack)` directly for consumed pedestals. The dedicated callback entry does not substitute a `hasContainerItem` gate. Borrowed item callbacks require the known container owners; GT lazy ItemList branches use existing source-bound projections. Source bindings and callback observations must remain valid at sealing. Full ore/name/template/input-order and container-return re-observations run at sealing rather than for every unrelated row. Shared ore-role bindings belong to the handler reader, and close releases owned specimens and source graphs.

Pedestal slots are replaced as a whole, not decremented as ordinary crafting inventory. Inputs therefore use `stack`, except a GTNH retention branch uses `keep`. TC4Tweaks Enhanced outer choices use `allocated` because startup membership does not determine cycle allocation; unused stock remains and shown returns are conditional on that pedestal being used. Displayed count one is a specimen. The source context creates an owned, worldless native `TilePedestal` solely for its inventory-limit getter. Constructor inspection found only owned inventory initialization; this batch has not executed that code. The captured limit is checked again before sealing, and returned/replacement counts use that limit. A live custom pedestal or persisted world state is outside the emitted specimens' guarantee.

GTNHLib's first replacement matches with the rule input as the OreDictionary wildcard target. Its subsequent retention check reverses the direction: the actual offered stack is the target, and item/metadata equality retains that whole stack even when the declared output has different NBT/count. Otherwise a copied output is installed subject to the pedestal limit, or null clears it without an ordinary container. Capture never passes the borrowed replacement output into the native inventory setter, which can mutate its count. The real registration table and NO_REPLACEMENT sentinel are source-bound. Missing merged state/helper disables the replacement policy while retaining its registered data; a partial/unknown merged shape is an error. This structural activation proof is not game execution evidence. The Mixin's possible persisted replacements after a prior interrupted craft remain an external altar-state condition, not an invented reset.
